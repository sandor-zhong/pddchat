# 拼多多商家申诉自动化工具 — 业务逻辑文档

面向对象：接手维护这个项目的开发者。描述系统"做什么、为什么这么做"，不是逐行代码注释——具体实现细节以对应源文件为准，本文档负责把分散在各文件里的业务规则串成一个整体。

---

## 1. 项目背景与整体架构

拼多多商家后台里，消费者对商品/服务给出负向评价或投诉后，平台会给商家一个有时限的"申诉"窗口：商家可以选择申诉理由、填写申诉说明、上传凭证图片，请求平台重新裁定。本项目把"发现可申诉订单 → 查看买卖双方聊天记录判断责任在谁 → AI 生成申诉文案 → 自动打开表单填写/上传凭证/提交"这一整套操作自动化，替代人工逐单处理。

支持单店铺，也支持多店铺并行/交替调度（多个拼多多商家账号同时或轮流处理）。有两套使用入口，背后共用同一套业务逻辑和同一个 SQLite 数据库：

- **命令行**（主项目，Python 3.12）：`main.py` 单店铺全流程 + `run_shops.py`/`run_shops_interleaved.py` 多店铺调度，面向开发者/技术人员调试和无人值守批量运行。
- **桌面 GUI**（`gui/` 子项目，独立 Python 3.11 环境）：面向不懂命令行的运营人员，见第 9 节。

技术栈：Playwright（浏览器自动化，同步 API）+ DeepSeek/火山方舟（AI 判断与文案生成、字符验证码识别）+ SQLite（`state/pddchat.db`，见第 7 节）。

## 2. 整体流程：三个阶段

### Phase 1 采集（collect）

入口：客诉申诉列表页 → 点击"查看可申诉订单" → 读取订单表格。

**关键设计：默认只读第一页**（`run_appeal_batch.py` 的 `collect_all_appealable_order_numbers(max_pages=1)`）。理由：每天新出现在第一页的订单处理完就够，不需要每次都翻遍所有历史积压页。这个设计的直接后果是——**如果一家店铺背后积压了很多页可申诉订单，需要连续跑好几天，每天吃掉当前的"第一页"，才能把历史积压处理完**；已提交的订单会从"可申诉"列表里消失，原来的第二页会自然顶上来变成新的第一页，不需要程序记录"翻到第几页了"这类进度游标。如需恢复"一次性翻页收集全部"的老行为，调用方可以显式传更大的 `max_pages`。

提取每一行的订单号 + 问题类型（`商品问题` / `服务问题`），记录到数据库 `orders` 表（`status=pending`）。同一订单号重复采集到不会覆盖它已有的状态（比如已经分析/提交过的订单不会被打回 pending）。

### Phase 2 分析（analyze）

对每个待处理订单：打开聊天记录查询页，按订单号查询买卖双方的聊天记录。

- **没有聊天记录的订单**：不调用 AI，直接固定判定为"消费者未表达商品问题"，用固定申诉文案（见第 4 节 `NO_CHAT_RECORD_APPEAL_TEXT`）。
- **有聊天记录的订单**：把聊天记录压缩成精简 JSON（去除多余字段、图片替换为 `[图片]` 占位符，省 token），调用 DeepSeek 大模型两次：
  1. 判断"申诉凭证类型"（三选一，见第 4 节）；
  2. 基于聊天记录 + 已判定的凭证类型，生成 100 字以内的申诉文案。

分析结果（凭证分类 + 申诉文案 + 聊天记录原文 + 消息条数）写入数据库（`status=analyzed`）。**已经分析过的订单默认跳过重新分析**（省 API 调用、避免同一订单每次跑出不同文案），除非显式要求强制重新分析（`--reanalyze`）。分析失败会截图存证、记为 `analysis_failed`，不影响其它订单继续处理。

### Phase 3 提交（submit）

对每个订单号：先搜索该订单号——**一个订单号在拼多多那边可能对应不止一条独立的"消费者负向体验"记录**（商品问题一条、服务问题一条，甚至同一问题类型也可能不止一条），逐条处理，互不影响（其中一条失败不会连累同一订单号下其它记录不被处理）。

每条记录：打开详情页 → 判定当前处于哪种"状态"（见第 3 节）→ 按状态类型走对应的表单流程（选申诉原因/理由 → 填申诉说明 → 上传凭证）→ 点"提交"或"取消"。

- 默认点**取消**（模拟提交，`status=simulated`）——验证整条自动化流程能不能走通，不产生真实后果，可反复调试。
- 显式开启真实提交（`--confirm`）才会点**提交**（`status=submitted`）——**不可撤回**。

### 默认运行模式：逐单交织

`main.py` 不带任何阶段参数时，默认走"逐单模式"：**每个订单分析完立刻处理提交，再进入下一单**，而不是"全部订单分析完，再全部提交"。这样"提交"的最小粒度精确到一个订单，才能支撑"提交完一单立刻换到另一家店铺处理"的多店铺调度器（见第 8 节）。显式指定 `--collect`/`--analyze`/`--submit` 任意一个时，退回原来"整批跑完再进入下一阶段"的分阶段批量流程，用于分步调试。

## 3. 申诉详情页状态判定

判定函数：`appeal_submit.py` 的 `detect_detail_page_status()`。依据详情页 `div.detail_status__2shmG` 区块里的文案 + class 锚点组合交叉判断，三处锚点仍冲突时直接抛 `RuntimeError`，**绝不做静默猜测**。

| 状态 | 识别条件 | 点"我要申诉"后的形态 | 表单控件 |
|---|---|---|---|
| **A** | 文案含"当前平台未采取实际处理措施" | 直接弹表单模态框 | radio + textarea + 图片上传（有示例缩略图） |
| **A2**（商品问题变体） | 与 A 共用锚点，模态框打开后 `#appealReasonCode` 只有 2 个 radio（"商品没有问题"/"其他"） | 同 A，弹表单模态框 | 固定选"其他"→渐进渲染出申诉说明+凭证上传 |
| **A3**（赔付类申诉变体） | 与 A/A2 共用锚点，模态框打开后 `#appealReasonCode` 有 3 个 radio | 同 A，弹表单模态框，多一段"仅对赔付款项申诉"提示（纯展示，不交互） | 固定选"其他"→渐进渲染，处理方式与 A2 完全一致 |
| **B** | class 含 `detail_confront_new_status`，"我要申诉"是 `<a>` 链接 | 先弹"确认要发起申诉吗"二次确认框（固定点"不认可，仍要申诉"）→再弹表单模态框 | radio（渐进渲染，另有 3 个默认已选中的必选项会显式重新点一遍做校验）+ 图片 |
| **C** | class 含 `detail_confront_new_status`（同 B），"我要申诉"是 `<button>` | 打开**新页面**（非模态框） | 下拉 select + textarea + 图片上传（选了下拉才渐进渲染后续字段） |
| `ALREADY_APPEALED` | 状态文本含"已申诉" | 无入口，直接跳过 | — |
| `EXPIRED` | 状态文本含"超时未申诉"（申诉窗口已过期，已被处罚） | 无入口，直接跳过 | — |
| `REJECTED` | 状态文本含"申诉未通过"（申诉过但没通过，已被处罚） | 无入口，直接跳过 | — |

终态识别标记集中在 `TERMINAL_STATUS_MARKERS` 字典（`appeal_submit.py`）里，`main.py` 侧对应 `_TERMINAL_STATUSES` 字典；以后新增一种终态文案，两处各加一行即可，不用改判断逻辑本身。

**这里识别的是详情页文案，且只在*重新提交*某个订单时顺带触发**——不是一个主动去查"审核结果出来没有"的功能。真正主动、周期性去查审核结果的是第 10 节的"查询申诉结果"，走的是完全不同的代码路径（列表页驱动，不进详情页），两边只是最终共用同一套 `status` 枚举。

**问题类型影响表单细节**：商品问题走上表 A/A2/A3/B/C 分支；服务问题的表单固定选"其他"，填说明、上传凭证（渐进渲染），不经过 A/B/C 的 radio 选择逻辑。

**表单里选项的申诉原则（不可动摇）**：所有分支都固定不承认商品本身存在质量问题——A/B/C 的 radio 只映射到"商品无问题，消费者误解"和"消费者未表达商品问题"两个选项，绝不选会承认商品有问题的选项；A2/A3 固定选"其他"。这个原则贯穿到第 4 节 AI 生成申诉文案的系统提示词里。

## 4. AI 分析逻辑细节

模块：`appeal_classifier.py`，模型：DeepSeek（`deepseek-v4-flash`，`base_url=https://api.deepseek.com`，需要环境变量 `DEEPSEEK_API_KEY`）。

### 申诉凭证类型判断（三选一）

1. **消费者所述问题经核验不存在** —— 买家反馈过具体问题，但没有提供照片/视频等有效凭证证明问题真实存在，问题始终没有被证实；或者商家已要求买家提供凭证但买家未能提供，或商家已主动给出处理方案（无论买家是否明确接受）。
2. **消费者误解商品信息** —— 买家对商品信息/功能/适用范围/使用方式存在误解，商品本身按详情页描述正常。
3. **消费者未表达商品问题** —— 买家全程只是咨询/提问/求助，没有明确反馈商品存在问题。

调用参数：`temperature=0`（要求判断结果稳定可复现）、`max_tokens=60`、关闭思维链（`thinking: disabled`，省 token）。

### 申诉文案生成

基于聊天记录 + 已判定的凭证类型生成，核心约束（写在系统提示词里，是这个功能的业务红线）：

- **全文任何地方都不能承认或暗示商品有问题**；买家提到的任何"问题"只能写成买家自己的反馈/反映/主观感受/误解，不能当作已查实的客观事实。
- 立场完全站在商家一方，只挑对商家有利的事实（买家没提供凭证、买家只是咨询/误解、商家已解释清楚或已履行客服义务、双方已有解决方案且买家未明确拒绝等），对商家不利或含糊的信息一律不提。
- 要引用聊天记录里的具体细节，不能空洞套模板，给出明确结论（"商品无问题""属于消费者误解""不应判责"之类）。
- 严格控制在 **100 个汉字以内**（含标点）；调用参数 `temperature=0.3`（比分类判断稍高一点，允许措辞有变化，但不追求创造性）、`max_tokens=200`；超过 300 字会被强制截断（正常情况下不应触发，是防御性兜底）。

**无聊天记录的固定兜底**：`NO_CHAT_RECORD_LABEL`（"消费者未表达商品问题"）+ `NO_CHAT_RECORD_APPEAL_TEXT`（固定文案）——查询不到聊天记录时，不经过大模型，直接用这一对固定值，节省一次不必要的调用。

**人工兜底入口**：`appeal_classifier.py --manual` 支持人工粘贴聊天记录文本走同一套分类+生成逻辑，是浏览器自动化被风控卡死时的应急手段，正常流程不会走到这里。

## 5. 验证码处理机制

模块：`captcha.py`。拼多多后台在任意页面、任意时刻都可能弹出验证码，分三类：

| 类型 | 识别方式 | 自动破解方案 |
|---|---|---|
| 旋转验证码 | 容器带 `captcha-wrapper__rotateslider` 类 | 截取背景图+圆形图 → 图片角度匹配算法算出最佳旋转角度（NCC 分数低于阈值直接放弃，不做低置信度硬拖）→ 换算成滑块拖动距离 → 拟人化轨迹拖动（贝塞尔缓动曲线、Y 轴随机抖动、中途随机停顿、末尾过冲回拉） |
| 字符验证码 | 容器带 `captcha-wrapper__text` 类 | 截图验证码图片 → 调用火山方舟视觉模型识别文字 → 拟人化逐字打字输入 |
| 其它/未知类型 | 都不匹配 | 不尝试自动破解，直接回退人工 |

**关键原则：程序绝不自动滑动"未知类型"验证码去猜绕过**——只对能可靠识别、有对应算法的两类做自动破解，其余一律让路给人工，验证码本身就是用来区分人和程序的。

**重试与放弃机制**：每种类型自动破解最多重试 3 次。3 次都失败之后走哪条路，由 `_give_up_after_auto_solve_fails` 这个模块级开关决定：

- **关闭**（默认值，`appeal_submit.py` 独立当脚本跑、有人守在浏览器前调试时的场景）：回退到等人工滑完，最长等 5 分钟，控制台响铃提醒。
- **开启**（`main.py` 登录成功后自动打开，见下）：直接抛异常，交给上层按"这一单/这次操作失败"处理并跳过，不再傻等一个不存在的人来处理。

`main.py` 在**登录成功之后**才调用 `set_give_up_after_auto_solve_fails(True)`——这是刻意的顺序：无人值守批量跑单场景下，采集/分析/提交这些逐单动作没必要为了等一个不存在的人干等 5 分钟；但**登录阶段本身不受这个开关影响，永远保留"等人工"这条路**，因为登录失败没有"下一单"可跳，放弃就等于直接放弃这整个店铺会话——这个区分点是本项目为"无人值守批量运行"专门做的取舍，不要在未来改动中不小心让登录也走上"放弃"分支。

## 6. 反爬虫应对与拟人化操作

模块：`stealth.py`（浏览器指纹与操作拟人化）+ `blockers.py`（弹窗清障）。

### 清障机制（`blockers.py`）

`clear_blockers()` 是统一清障入口，按优先级处理：

1. **验证码** → 走第 5 节的流程，绝不代劳；
2. **通知类弹窗**（右上角 X / "知道了"类纯确认按钮）→ 自动关掉；**只点关闭类控件，绝不触碰弹窗里其它按钮**，避免误触"提交""确认""删除"这类会产生真实后果的操作；
3. **认不出的遮挡物** → 存档（HTML + 截图）+ 响铃，等人工处理；
4. 干净 → 立刻返回，几乎零开销。

两个点击辅助函数职责不同、**不能互换**：

- `safe_click`：在 modal *打开之前*用（列表页、按钮、链接）。点击前会 `clear_blockers`，遇挡自动重试。
- `stealth_safe_click`：在 modal *已经打开*时用（表单内部的单选/上传等操作）。**绝不调用 `clear_blockers`**——那会把当前正在操作的模态框本身误判成通知型弹窗关掉，把用户正在填的表单一起弄没。

### 拟人化操作（`stealth.py`）

- 关键步骤之间插入随机延迟（`human_delay`/`jitter_wait`），避免机械的毫秒级连续操作；
- `human_type`：逐字模拟打字（而非一次性 `fill()`），用于验证码输入框、申诉说明文案填写等场景；
- 滑块拖动轨迹是贝塞尔缓动曲线 + Y 轴随机抖动 + 中途随机停顿 + 末尾过冲回拉，不是线性匀速拖动（见第 5 节）；
- 浏览器上下文用"隐身"模式创建（`create_stealth_context`），配合按店铺持久化的用户数据目录（`state/profiles/<shop>/`）保存登录态。

## 7. 数据存储

模块：`db.py`，单一 SQLite 文件 `state/pddchat.db`，**一个数据库覆盖所有店铺**（不按店铺分文件）。存储时间统一用 **UTC**（`datetime.now(timezone.utc).isoformat()`），展示层（GUI/`--status`）负责转本地时区，见第 9 节。

刻意设计成**零第三方依赖**（只用 `json`/`sqlite3`/`datetime`/`pathlib`），且不依赖任何环境变量固化路径（`shop` 都是显式参数）——这是全项目唯一能被 GUI（独立 Python 3.11 环境）安全直接 `import` 的业务模块，其它涉及浏览器操作的模块都间接依赖 `paths.py`（import 时读 `PDDCHAT_SHOP` 环境变量固化路径），GUI 进程绝不能直接 import。

### `orders` 表（主键 `shop` + `order_no`）

订单级别的状态机，覆盖采集→分析→提交全链路：

| 字段 | 说明 |
|---|---|
| `issue_type` | 商品问题 / 服务问题（同一订单号名下多条记录可能拼接成"商品问题、服务问题"） |
| `status` | `pending`（已采集未分析）/ `analyzed`（已分析未提交）/ `analysis_failed` / `simulated`（模拟提交，点了取消）/ `submitted`（真实提交，等结果）/ `already_appealed`（详情页发现已申诉过，等结果）/ `not_found` / `submit_failed`（提交动作本身失败）/ `expired`（申诉窗口过期已处罚）/ `rejected`（申诉未通过已处罚）/ `approved`（申诉通过）/ `review_unknown`（查到了一个还没见过的审核结论文案，原文存在 `error_message` 里，等确认后扩充词表）——最后四个是拼多多的**审核结论**，跟其它状态"我们这边做到哪一步了"是不同维度，可能通过第 3 节（重新提交时详情页顺带识别）或第 10 节（主动查询）两条路径中的任意一条写入，详见第 10 节 |
| `classification` / `appeal_text` | AI 判定的申诉凭证类型 + 生成的申诉文案 |
| `messages` / `message_count` | 聊天记录原文（JSON）+ 消息条数 |
| `evidence_paths` | 凭证截图相对路径列表（JSON 编码），二进制文件本身仍在 `evidence/`/`debug/` 目录，不进数据库 |
| `error_message` / `error_screenshot_path` | 失败原因 + 失败现场截图；**任一已知成功状态写入时，`error_message` 会被清空**——避免界面上一边显示"已提交成功"、一边还挂着一条过时的失败原因 |
| `form_screenshot_path` | 服务问题/部分场景下的填表后截图 |
| `collected_at` / `analyzed_at` / `submitted_at` / `updated_at` | 各阶段时间戳，均为 UTC |

### `shop_daily_status` 表（主键 `shop` + `run_date`，`run_date` 为本地日期）

店铺 + 日期粒度的"今日调度周期"状态——`orders` 表只知道单个订单的结果，回答不了"这家店铺今天这一轮采集/调度周期本身有没有跑完"。调度器靠这张表决定"今天要不要为一家店铺开浏览器"：

| `status` | 含义 | 写入时机 |
|---|---|---|
| `done` | 今天这一轮正常跑完（不管处理了 0 单还是很多单） | 队列清空（`queue_empty`）或 init 阶段发现没有可处理订单 |
| `failed` | 遇到没解决的问题（登录失效、连续失败达阈值、通信中断等） | 各类异常分支 |
| `skipped` | 本轮并发名额不够，压根没轮到开工（跟 `failed` 不同，不是这家店自己有问题） | 一轮结束时，`pending` 列表里还剩下的店铺（见第 8 节"跨天优先级"） |
| （无记录） | 尚未开始，**或**已经进入处理但被中途打断（比如到点被优雅停止），未达到任何终态 | — |

**只有"无记录"和 `done` 两种情况有明确语义边界，`failed`/`skipped` 都不是"跳过"，下次查询照样会把这家店铺纳入待处理**——这是"没有记录/没有终态 = 下次会被重试"这条核心约定的具体体现，保证批量运行中途被打断（GUI 关闭、点停止、跨天）不会漏掉任何一家店铺，见第 8 节。

**`run_date` 是本地日期，`updated_at` 是 UTC**——两者理论上可能不一致（尤其中国时区 UTC+8，UTC 零点恰好等于本地早上 8 点），查询/展示这张表时不要混用两种时间语义做判断。

### `appeal_records` 表（主键 `shop` + `order_no` + `record_key`）

同一订单号在拼多多那边可能对应多条独立的"消费者负向体验"记录，`orders` 表按 `(shop, order_no)` 一行的粒度存不下"第几条记录是什么状态"，所以单独开这张表，`record_key` 从记录所在行文本里提取（一般是创建时间）。分析结果（聊天记录/AI 判定/申诉文案）不重复存在这里——那些基于聊天记录判断，跟"第几条负向体验记录"无关，同一订单号的多条记录共用 `orders` 表里那一份分析结果；这张表只存**提交结果**（`status`/`error_message`/两种截图路径/`submitted_at`）。

## 8. 多店铺调度（`scheduler_core.py`）

`scheduler_core.py` 是从早期的 `run_shops_interleaved.py` 抽出的、**不依赖任何 UI 框架**的可复用调度核心，`run_shops_interleaved.py`（CLI）和 GUI 的"运行控制"页都通过这一个 `Scheduler` 类驱动，两边自动获得一致的行为。

### 进程模型

每个被调度的店铺是一个**常驻**子进程（`python main.py --shop <shop> --serve`），浏览器全程开着，不是每单都重启。调度器和子进程之间通过 stdin/stdout 上一个极简 **JSON Lines 协议**通信：

```
调度器 → 子进程：{"cmd": "init"}   首次取得发言权时发，才真正开浏览器+登录检测+采集，回 ready
                {"cmd": "next"}   处理队列里下一单，回 result / queue_empty / error
                {"cmd": "stop"}   关浏览器，退出
子进程 → 调度器：{"type": "ready", "queue_size": N}
                {"type": "result", "order_no": "...", "result": "..."}
                {"type": "queue_empty"}
                {"type": "error", "stage": ..., "message": ...}
```

子进程故意**不在启动时立刻开浏览器**，而是延后到收到第一条 `init` 才真正启动——避免调度器一次性 `Popen` 出 N 个店铺子进程时，它们几乎同时各自连拼多多，与"同一时刻只有一家在操作"的初衷相反。协议消息编码显式钉死 UTF-8（调度器与子进程两端都显式 `reconfigure`），不吃系统 locale 默认值（Windows 常见 cp936），否则中文内容会在管道里悄悄错位/乱码但不报错，调度器靠字符串前缀判断结果的逻辑会全部失灵却毫无提示。

### 并发池与补位

- `pool_size`（并发上限，默认 4）：同一时刻最多这么多家店铺的浏览器同时开着；
- 每轮开始，计算 `pending`（今天还没跑完的店铺）→ 按优先级排序（见下）→ 依次 `_start_worker` 补进 `active` 直到占满 `pool_size`；
- 某家店铺处理完（`queue_empty`）或判定异常（见下）关闭让位，立刻从 `pending` 里拉下一家补上；
- 在"池子里当前打开的几家"之间**随机点名**"该你了"处理下一单，且不会连续两次点同一家（只剩一家时除外）——这是"逐单跨店随机"名字的由来；
- 因为浏览器操作完全在各自子进程里单线程执行，"同一时刻只有一家店在真正操作"是协议本身保证的，不依赖锁。

### 连续失败熔断

某店铺连续失败达到阈值（默认 3 单，`max_consecutive_errors`）时判定为"可能登录失效或其它持续性异常"，关闭浏览器让位，落 `shop_daily_status.status='failed'`，下一轮/下一天会重新尝试（不是永久放弃）。

### 跨天状态语义与"跨天优先级"

以 A~G 七家店铺、并发数 3 为例，说明为什么整批店铺可能要跑好几天：

1. **每天只吃"当前第一页"**（第 2 节）——背后积压好几页的店铺，天然需要好几天才能翻完历史积压，与并发数、排队与否无关。
2. **并发数限制**——勾选店铺数超过并发数时，排不上号的店铺当轮结束时会被标记 `shop_daily_status.status='skipped'`（而非"失败"，因为这家店本身没问题，只是没抢到名额）。
3. **跨天优先级**（`Scheduler._skip_priority`/`_order_pending_by_priority`）：排队顺序不是纯随机——**连续被标记 `skipped` 的天数越多，下一轮排队排得越靠前**（往前最多回看 14 天，`SKIP_PRIORITY_LOOKBACK_DAYS`），直到真正被处理一次（`done`/`failed` 都算"处理过"，连续计数会断开）为止；同一优先级内部仍然随机，避免"名字靠前的永远优先"这种新的不公平。这个机制专门解决"店铺数多于并发数时，同一批大店铺持续挤占名额、小店铺被无限期挤占"的问题。
4. **`shop_daily_status` 按日期分区，不跨天生效**——今天 `done` 只代表今天这一轮跑完了，明天是全新的一天，所有勾选的店铺都会被重新纳入判断（没有新单的店铺会在 init 后立刻发现队列为空、秒速标记 `done` 关闭，不会占用太久）。
5. **被中途打断（比如到点优雅停止）的店铺没有终态记录**，跟"排不上号"的 `skipped` 不是一回事——它已经开始处理、只是没来得及处理完，下次会自然从"当前的可申诉列表第一页"（已提交的部分已经不在列表里）继续，不需要专门的续传/游标逻辑。

### 优雅停止

`Scheduler.request_stop()` 线程安全，可从任意线程调用。各处等待点用短轮询（`threading.Event.wait(min(remaining, 1.0))`）代替一次性长 `sleep`，让停止请求能在约 1 秒内打断，同时仍允许合法的长耗时操作（比如人工手动过验证码，最长 30 分钟）在超时前正常完成。**不会打断正在处理中的这一单**——只是不再开始新的一单/新店铺；收尾时给所有仍存活的子进程发 `stop` 优雅关闭，超时未退出兜底 `terminate()`。

### 全局锁

`state/scheduler.lock` 文件（`{"pid", "started_at", "shops"}`），防止 GUI 的"运行控制"页和手动跑的 CLI 调度器同时对同一店铺开浏览器互相冲突：

- `Scheduler._run()` 开头尝试获取锁：锁文件不存在，或存在但里面的 PID 已经不在跑了（上次没走到 `finally`，比如被强杀）→ 覆盖写入自己的信息、拿到锁；锁文件存在且 PID 还活着 → 拿不到锁，直接返回（不开任何浏览器）；
- PID 存活性用 Windows `ctypes` 调 `OpenProcess`+`GetExitCodeProcess` 直接查真实进程状态，不用"心跳超时"这种模糊判断——不会因为一次验证码人工处理等了很久就被误判成"锁过期"；
- 释放时确认锁文件里的 PID 仍是自己才删，避免误删别的进程刚好抢到的新锁；
- GUI 新增店铺/重新登录前会只读检查一次这把锁，冲突时提示但不强制阻止（用户可以选择"仍要继续"）。
- **明确不覆盖**：`run_shops.py`（更早期的纯顺序调度器，不经过 `Scheduler`）；不做按店铺粒度的细粒度锁，是"全局只能有一个调度进程"的粗粒度保护，对单人操作场景够用。

## 9. GUI 架构

`gui/` 是独立子项目，**独立的 Python 3.11 环境**（PyQt5，与主项目 Python 3.12 环境完全隔离），只通过以下两种方式与主项目交互：

1. **直接 `import`**：`db.py` 和 `scheduler_core.py`——两者都是零第三方依赖的纯标准库模块，GUI 通过把主项目根目录插入 `sys.path` 后直接导入使用；
2. **子进程调用**：任何真正涉及浏览器/Playwright 的操作（登录、批量运行）一律通过 `subprocess.Popen` 起主项目 Python 环境的 `main.py`，GUI 进程自己永远不 import `login.py`/`captcha.py`/`main.py` 等依赖 Playwright 的模块。

四个页面：

- **A 总览仪表盘**：顶部统计卡片（店铺总数/今日已完成/待处理订单/今日已提交/今日失败）+ 逐店铺卡片（登录状态、今日调度状态、待处理/已提交/已跳过/失败数、最近活动时间）。
- **B 店铺管理**：表格形式（店铺名/登录状态/今日状态/最近活动/启停状态），右键菜单：重新登录 / 停用或启用 / 重置今日状态（允许重新处理，见第 8 节 `shop_daily_status`）/ 删除（只删登录态目录，保留历史订单数据）。"新增店铺"走轻量登录子进程模式（`--login-only`，轮询检测登录完成，不阻塞等终端回车）。
- **C 运行控制**：勾选参与本轮的店铺 + 并发上限 + 启动/优雅停止按钮 + 实时状态迷你表格 + 滚动日志（同时落盘到 `gui/state/logs/`，按天滚动保留 14 天）。固定真实提交前二次确认，固定自动破解验证码优先、不强制重新分析、跑完勾选的这批店铺就自然停止（对应 `Scheduler.run_once()`）。
  - **每日定时自动运行**：开关默认关闭，首次从关到开会弹一次性确认（讲清楚"以后每天这个时间窗自动真实提交，不会再逐次确认"），之后每天到点自动启动（等效于自动点一次"启动"，用当时勾选的店铺）、到点自动优雅停止（等效于自动点一次"优雅停止"，不打断正在处理的订单）。这是 GUI 内置定时器，**依赖 GUI 进程本身保持运行**，不是系统级计划任务。
  - **关闭确认**：直接关闭窗口时，如果批量任务正在跑，会拦截一次，询问要不要先优雅停止（最长等待 30 秒，超时可选择强制关闭或继续等待）——避免浏览器子进程没有被正常清理成为孤儿进程。
- **F 报表/导出**：按店铺 + 时间范围（全部/今天/近 7 天/近 30 天）筛选，图表（PyQtChart）+ 明细表（`orders` 表全量字段）+ 导出 Excel/CSV + 凭证截图预览（填表后截图/错误现场截图）。

**时间展示统一转本地时区**： 数据库存储用 UTC 是正确的存储实践，但直接把 UTC 字符串显示给用户容易造成"时间对不上"的困惑（中国时区与 UTC 相差 8 小时），GUI 所有面向用户的时间展示（最近活动、提交时间等）以及导出的 Excel/CSV 都统一经过 `time_format.format_local()` 转换成本地时区再显示，不需要用户自己心算时差。

## 10. 查询申诉结果

模块：`check_appeal_results.py`，独立文件，不改动 `appeal_submit.py`/`run_appeal_batch.py`。

### 要解决的问题

拼多多审核一条申诉一般要 1-2 个工作日才出结果（通过/驳回），而第 2/3 节的采集-分析-提交流程是"发申诉"，不负责"回头看结果出来没有"。这个功能补上"回头看"这一步：进客诉申诉列表页，按日期区间筛选，把已经出结果的记录同步回数据库。

### 跟第 3 节"详情页终态判定"的关系：两条独立路径，共用同一套枚举

| | 第 3 节（`appeal_submit.TERMINAL_STATUS_MARKERS`） | 本节（`check_appeal_results.py`） |
|---|---|---|
| 触发时机 | 重新提交某个订单时，打开详情页顺带识别到 | 主动、周期性调用，跟提交流程完全解耦 |
| 读取的页面 | 申诉详情页 | 申诉列表页（不进详情页） |
| 能覆盖的场景 | 只有"又被处理到"的订单才会被看到 | 日期区间内所有订单，不依赖"是否又被处理到" |

两条路径**互不调用**，但最终都落到 `db.record_submit_result()`/`db.record_appeal_result()` + `db._SUBMIT_STATUS_MAP` 这同一套映射机制上——不管从哪条路径查到"申诉未通过"，落库的都是同一个 `status="rejected"`，不会出现"两套说法"。

### 查询范围：只查"已提交、还没有结果"的本地订单

`CHECK_RESULT_STATUSES = ["submitted", "already_appealed", "review_unknown"]`——先查一遍本地数据库有哪些订单满足这个条件，才去拼多多那边翻页比对，不是把列表页翻个遍再挨个查数据库。

刻意不包含的状态，各自的理由：

- `simulated`（模拟提交，点的是"取消"）——压根没有真的发给拼多多，没有真实审核结果可查；
- `rejected` / `expired` / `approved`——已经是终态，默认不再复查（如果发现拼多多的审核结论会被后续翻案，把对应状态加进这个列表即可，不用改其它逻辑）。

### 处理状态文案 → 内部词汇 → `status` 枚举

客诉申诉列表页"处理状态"列（真实页面核实于 2026-08-20）会出现 5 种文案，`APPEAL_RESULT_TEXT_MAP` 负责翻译：

| 页面原文 | 是否终态 | 翻译成的内部词汇（喂给 `db.py`） | 落库 `status` |
|---|---|---|---|
| 可申诉 | 否 | — | 不落库（正常不该出现在我们关心的订单里，出现了大概率是本地状态跟拼多多不同步） |
| 已申诉 | 否 | — | 不落库，本地状态原样不动 |
| 超时未申诉已处罚 | 是 | `已超时-跳过`（复用第 3 节已有的词） | `expired` |
| 申诉通过 | 是 | `已通过`（新词） | `approved` |
| 申诉未通过已处罚 | 是 | `已驳回-跳过`（复用第 3 节已有的词） | `rejected` |

两个"终态"文案复用第 3 节已经在用的内部词汇（而不是各自发明一套），是为了让这两条路径查到同一种结果时精确落到同一个 `status` 值，见上一小节。

**未登记的新文案不会被丢弃**：`db.record_submit_result()`/`db.record_appeal_result()` 新增了一个 `fallback_status` 参数（默认 `"submit_failed"`，所有原有调用方零改动、行为不变），本功能显式传 `fallback_status="review_unknown"`——因为这条路径下"没认出来的文案"通常意味着"成功读到了一个还没见过的审核结论"，跟"提交这个动作本身失败了"是两回事，原始文案会保留在 `error_message` 里，不静默丢弃，下次再查到同一条记录时也还会被 `review_unknown` 状态继续纳入复查范围（见上上小节）。

### 日期区间选择器

页面是 beast-core 的 rangePicker：点触发器弹出两张并排的月历表格（一张较早、一张较晚），点两天定下区间首尾，两张表格由同一对左右箭头整体翻页。`set_date_range()` 处理了两个容易出错的细节：

1. **跨月边界**：默认查最近 3 天，月初 1-3 号时"3 天前"会跨到上个月——不是简单假设两个目标日期都在当前默认显示的月份里，而是每次都先检查当前两张表格显示的年月，需要翻页就自动翻，不局限于"只翻一次"。
2. **同一数字的歧义**：月历格子里，月初/月末常见"借用"相邻月份的填充格子（比如同一张表格里"1"可能出现两次：一次是本月 1 号，一次是下月填充进来的 1 号），必须先排除带有"不属于本月"标记的格子，才能按数字精确点到"这个月自己的那一天"。

选择器定位优先用 `data-testid`（比如 `beast-core-rangePicker-input`/`beast-core-icon-left`）而不是 CSS class——这批 class 名带构建哈希后缀（例如 `RPR_dateText_5-163-0`），前端一重新构建就可能整体变掉；只有"排除填充格/禁用格"这两处没有 testid 可用，退而用 class 名里包不包含 `outOfMonth`/`disabled` 这种关键词子串匹配，不依赖完整哈希后缀，尽量减少以后前端改版带来的维护成本。

### CLI 与 GUI 集成

- `main.py` 新增 `--check-appeal-results`（必须搭配 `--shop`）+ `--since-days`（默认 3）。协议跟 `--login-only` 是同一种"`real_stdout` 单独发协议 JSON、`stderr` 走人类可读日志"的模式，但不需要等 `{"cmd": "close"}`——整个检查是同步跑完的，一次性子进程，跟 `run_appeal_batch.py` 的 `main()` 收尾方式一样直接关浏览器退出。
- GUI 侧新增 `AppealResultCheckWorker`（`gui/app/workers/appeal_result_check_worker.py`），C 页新按钮"查询申诉结果"驱动。**不复用第 8 节 `scheduler_core.Scheduler` 那套并发 worker 池**——那一套是为"多店铺同时开、单店铺内逐单交织"设计的，这个功能每家店铺只是"开一次浏览器、翻几页、关掉"的一次性动作，没有"下一单"这个概念，套用会是过度设计。改成对勾选的店铺**严格顺序**起子进程，一次只跑一家，既不需要并发，也天然避免这个功能自己跟自己抢同一个店铺的登录态目录。
- C 页"启动"和"查询申诉结果"互斥（双向）：任何一个在跑的时候，另一个的入口（手动点击、以及"每日定时自动运行"的自动触发）都会被挡住，等当前这个结束——两边都要用同一批店铺的 Chrome 登录态目录，同时跑会互相冲突。
- F 页新增 `DbPoller`（4 秒轮询，跟 A/B 页同款），查询过程中/查询完之后写入的新结果不需要手动点"刷新"就能看到——这条路径写库的进程（不管是 GUI 按钮触发，还是纯命令行跑 `--check-appeal-results`）都在 F 页所在的 GUI 进程之外，F 页本身并不知道数据什么时候变了，必须靠轮询而不是事件通知。

### 全局锁的态度：跟"新增店铺"一致，只提示不强制

第 8 节提到的 `state/scheduler.lock` 是 `scheduler_core.Scheduler` 专用的锁，`--check-appeal-results` 子进程不获取这把锁（这个功能本身没有用 `Scheduler`）。GUI 侧点"查询申诉结果"前会只读检查一次这把锁的状态，冲突时提示但不强制阻止（跟 B 页"新增店铺"前的检查是同一个先例）——防不住命令行同时手动跑的极端情况，是"够用的软保护"而不是强一致性保证，本项目目前所有涉及这把锁的地方都是同一个尺度，没有为这一个功能单独做得更严格。
