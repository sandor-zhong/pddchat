# 新手代码阅读指南

面向对象：第一次接触这个项目源码的人，假设你会基本的 Python 语法（函数、类、if/for），但不一定用过 Playwright、PyQt5、SQLite，也不一定接触过"进程间通信"这类概念。

本文档不重复讲业务规则（那是 [业务逻辑文档.md](业务逻辑文档.md) 的事），只讲**代码本身怎么组织、用了什么写法、该按什么顺序去读**。建议对照本文档，把源码文件在编辑器里同时打开，边看边读。

---

## 1. 先搞清楚这是个什么项目

用一句话概括：**一个用浏览器自动化脚本操作拼多多商家后台网页的工具**，外加一个可选的桌面图形界面。

它不是网站，不是后端服务，运行方式就是"在电脑上执行一个 Python 文件"，执行的时候会真的弹出一个 Chrome 浏览器窗口，代码去操纵这个浏览器点来点去，就像录了一段"人在电脑前操作"的动作脚本反复播放。这个技术叫**浏览器自动化**，用的库是 [Playwright](https://playwright.dev/python/)。

项目里有两套代码，是**两个独立的 Python 环境**：

- **主项目**（仓库根目录下的 `.py` 文件）：跑在 Python 3.12，装了 Playwright、AI 调用库等，负责所有"真的去操作浏览器"的事情。
- **`gui/` 子目录**：一个独立的桌面图形界面项目，跑在自己单独的 Python 3.11 环境（PyQt5），**完全不装 Playwright**。它不会直接操作浏览器，而是"叫"主项目的代码去干活（具体怎么叫见第 6 节）。

为什么要分两个环境，看第 2 节的目录地图后会更清楚。

## 3. 读这份代码之前，几个你可能没见过的写法

### 3.1 文件开头都有 `from __future__ import annotations`

这一行让函数签名里写的类型（比如 `def foo(x: str | None) -> list[str]:`）只是给人看、给编辑器做提示用的，Python 运行的时候不会真的去检查类型对不对。**这不是这个项目独有的写法，是 Python 类型注解的标准用法**，不影响你读代码——遇到 `str | None` 就理解成"这个参数可能是字符串，也可能是 None（没有值）"，`list[str]` 就是"字符串组成的列表"。

### 3.2 `@dataclass`

`scheduler_core.py` 里的 `SchedulerEvent`：

```python
@dataclass(frozen=True)
class SchedulerEvent:
    type: str
    shop: str | None
    data: dict = field(default_factory=dict)
    line: str = ""
```

这是 Python 标准库的一个"少写点样板代码"的工具——不用你自己写 `__init__` 方法，加了 `@dataclass` 之后，Python 自动帮你生成"接收这几个字段、存到 self 上"的构造函数。`frozen=True` 表示这个对象创建之后不能再改字段的值（只读），适合用来表示"一个已经发生的事件"，防止某处代码不小心改了它。

### 3.3 Playwright 的几个核心概念

这是最值得花时间弄懂的部分，因为 `appeal_submit.py`/`pdd_chat.py`/`login.py` 这些文件几乎每一行都在用。

- **`Page`**：一个浏览器标签页。`page.goto(url)` 就是在这个标签页里跳转到某个网址。
- **`Locator`**：**"怎么在页面上找到某个元素"的描述**，不是元素本身。比如 `page.locator("button")` 只是说"页面上所有 `<button>` 标签"，这时候浏览器可能还没加载完，甚至这个按钮根本还不存在——Playwright 会等到你真的用它（比如调 `.click()`）的时候才去页面上找，找不到就等一会儿再找，这是 Playwright 跟传统爬虫库最大的区别，**不需要你自己写"sleep 一秒再找"这种代码**。
- **链式调用**：`page.locator("button").filter(has_text="提交").first` 这种写法，每一步都是"在上一步的基础上进一步收窄范围"，最后 `.first` 表示"如果匹配到好几个，只要第一个"。读的时候从左到右念："页面上的 button 元素 → 再筛选出文字包含'提交'的 → 取第一个"。
- **`Locator.click()`/`.fill()`/`.wait_for()`**：分别是"点击"、"填文字"、"等到这个元素出现/消失"。
- **`BrowserContext`**：一个"浏览器会话"，可以理解成一个独立的、带自己 cookie/登录态的浏览器实例，一个 `Context` 可以开好几个 `Page`（标签页）。这个项目里每个店铺对应一个独立的 `Context`（登录态存在 `state/profiles/<店铺名>/` 目录下）。

### 3.4 满天飞的 `try/except` + `print` + 继续处理下一个

打开 `main.py` 会看到大量这种模式：

```python
try:
    ... 处理一个订单 ...
except Exception as exc:
    print(f"订单 {order_no} 处理失败: {exc}")
    ... 记录失败状态 ...
    # 不重新抛出异常，函数正常返回
```

这是**故意的**，不是偷懒。这个项目要批量处理几十上百个订单，**其中一个订单出错（网络抖动、页面结构变化）不应该让整批全部中断**——记录下这一单失败了，继续处理下一单，比"一出错就整个程序崩溃退出"更符合"批量处理"这个场景的需求。读代码时看到 `except Exception` 不用觉得奇怪，这是这个项目统一的容错哲学。

### 3.5 大量的中文文档字符串（docstring）

几乎每个函数上面都有一段三引号 `"""..."""` 包起来的中文说明，很多时候比代码本身还长。**这些不是可有可无的注释，是理解"为什么这么写"的关键**——很多设计背后有排过的坑（比如"为什么不能用 A 方法必须用 B 方法"），直接读代码看不出原因，读文档字符串才知道。**读这个项目源码的正确姿势是文档字符串和代码一起读，不要跳过。**

## 5. 数据库部分（`db.py`）——建议第一个细读的文件

`db.py` 用的是 Python 标准库自带的 `sqlite3`，不需要额外装数据库软件，数据库就是一个文件（`state/pddchat.db`）。这个文件适合新手第一个细读，因为它：

- 逻辑独立，不需要先懂 Playwright 就能看懂；
- 代码量适中（676 行），但重复模式很多，看懂一个函数基本就懂了大半；
- 是理解整个项目"状态是怎么记录、怎么判断下一步该干什么"的关键。

几个要点：

- **单例连接**：`get_connection()` 用一个全局变量 `_connection` 存着，第一次调用时才真正连接数据库，之后每次调用都返回同一个连接对象，不用每次查询都重新连一次。
- **参数化查询**：所有 SQL 语句里用 `?` 占位，真正的值通过第二个参数传进去（比如 `conn.execute("SELECT * FROM orders WHERE shop=?", (shop,))`），**不要改成用 f-string 直接把值拼进 SQL 字符串里**——`?` 占位是防止 SQL 注入攻击的标准做法，也顺便处理了字符串里带特殊符号的问题。
- **`conn.row_factory = sqlite3.Row`**：设置了这个之后，查询结果可以像字典一样用 `row["字段名"]` 取值，不用记"这是第几列"这种容易出错的写法。
- **三张表**：`orders`（订单状态）、`shop_daily_status`（店铺每天的调度状态）、`appeal_records`（同一订单号下多条申诉记录各自的提交结果），字段含义见《业务逻辑文档》第 7 节，这里只关心"怎么读写"这层技术实现。

## 6. 多店铺调度部分怎么读

这部分（`scheduler_core.py` + 主项目 `main.py` 里的 `--serve` 分支）涉及一个新手可能没接触过的概念：**进程间通信**，建议先读完前几节、对项目主流程有感觉了再来看这块。

### 6.1 用大白话理解这个设计

假设你要同时处理好几家店铺，最直接的想法是"开好几个浏览器窗口，一个个手动切换点"。这个项目的做法是：**让电脑同时跑好几个独立的 `python main.py` 进程**（每个负责一家店铺，自己开自己的浏览器），再用**另一个"调度员"进程**去指挥这几个进程"现在轮到你处理一单"、"你先歇着"。

调度员进程和干活进程之间怎么"说话"？——**通过一行一行的文本**。调度员进程用 Python 内置的 `subprocess` 模块启动干活进程（就像在命令行里手动敲一条命令，但是由代码帮你敲），启动之后两边通过**标准输入/标准输出**传消息，每条消息是一行 JSON 文本（比如 `{"cmd": "next"}` 表示"处理下一单"）。这种"一行一个 JSON"的做法有个名字叫 **JSON Lines**，好处是简单可靠，不需要引入更复杂的通信框架。

### 6.2 建议阅读顺序

1. 先读 `main.py` 里 `run_serve_mode()` 函数的文档字符串（不用看实现），搞懂协议长什么样（调度员发什么指令、干活进程回什么消息）；
2. 再读 `scheduler_core.py` 里 `ShopWorker` 类——这是调度员这边"管理一个干活进程"的对象，`send()` 方法负责发指令，`wait_response()` 负责等回复；
3. 最后读 `Scheduler` 类的 `_run_loop()` 方法——这是真正的调度逻辑："现在该让谁干活、谁做完了该关掉、该补哪个进来"。

### 6.3 一个新手容易疑惑的点：为什么不用更"正规"的多进程/多线程方案？

因为浏览器操作本身很慢（网络请求、页面渲染、验证码等待），用简单的"起独立进程 + 文本管道通信"就完全够用，不需要引入线程锁、共享内存这类更复杂、更容易出 bug 的东西。这也是为什么调度逻辑里完全没有出现 Python 的 `threading.Lock` 之类的锁——因为压根不需要，每个干活进程自己是完全独立的操作系统进程，天然不会互相干扰对方的浏览器操作。

## 7. GUI 部分（`gui/`）怎么读

如果你没用过 PyQt5（或者任何类似的桌面 GUI 框架，比如 Tkinter、Qt for C++），有几个概念要先建立：

### 7.1 信号与槽（Signal / Slot）

PyQt5 的核心设计：一个控件（比如按钮）"发出信号"（比如"我被点击了"），另一段代码"连接"到这个信号上（"一旦被点击，就执行这个函数"）。写法大概是：

```python
self._start_button.clicked.connect(self._on_start_clicked)
```

意思是"这个按钮的 clicked 信号，一旦发出，就调用 `self._on_start_clicked` 这个方法"。**不是"每隔一段时间检查一下按钮有没有被点"，而是事件驱动的**——点了才会触发，没点就什么都不发生。整个 GUI 代码里到处都是这种"信号连接"，读的时候找 `.connect(` 关键字，就能顺藤摸瓜找到"这个操作实际会调用哪个函数"。

### 7.2 为什么要用"后台线程"（`workers/` 目录）

GUI 有个规矩：**界面主线程不能被"耗时的事情"占住**，不然窗口会卡死、点了没反应、看起来像"未响应"。可是"跑批量申诉"这件事，从几分钟到几小时不等，**不能在主线程里直接跑**。

`workers/` 目录下的几个类（比如 `SchedulerWorker`）就是解决这个问题的：把耗时的操作挪到一个"后台线程"里跑，跑的过程中通过信号把"进度""结果"发回主线程，主线程收到信号后再去更新界面（比如往日志框里加一行文字）。**耗时的活在后台干，界面只负责"收到消息就刷新一下显示"，两边不会互相卡住**。

### 7.3 举个具体例子：点"启动"按钮之后发生了什么

1. `run_page.py` 里 `self._start_button.clicked.connect(self._on_start_clicked)`——点击触发 `_on_start_clicked`；
2. `_on_start_clicked` 弹出真实提交确认框，确认后调用 `_start_run(...)`；
3. `_start_run` 创建一个 `QThread`（后台线程）和一个 `SchedulerWorker`（包了一层 `scheduler_core.Scheduler` 的对象），把 `SchedulerWorker` "移动"到这个后台线程里（`moveToThread`），然后启动线程；
4. 后台线程里，`SchedulerWorker` 真正去调用 `scheduler_core.Scheduler`（第 6 节讲的那套调度逻辑，包括起子进程、JSON Lines 通信全在这个后台线程里跑）；
5. `scheduler_core.Scheduler` 每发生一个事件（处理完一单、某店铺出错……），就调用一次事先传进去的回调函数，这个回调函数把事件包成一个 PyQt5 信号发出去；
6. 主线程里 `run_page.py` 的 `_on_event` 方法收到这个信号，往界面上的日志框、状态小表格里更新内容。

这条链路是这个项目 GUI 部分最核心的设计，建议对照 `run_page.py`、`workers/scheduler_thread.py`、`scheduler_core.py` 三个文件一起看。

### 7.4 `services/` 目录的定位

`services/` 下的文件都是**不碰任何界面控件、纯逻辑/数据处理**的代码（读数据库、格式化时间、存取配置文件……）。这是一种常见的代码组织原则：**界面代码（`pages/`）只管"怎么显示、怎么响应点击"，具体的数据逻辑交给单独的模块**，这样以后如果要给某个功能写自动化测试，或者要把这块逻辑复用到别的地方，不需要牵扯到一整个界面控件。

## 8. 改代码/调试的一些实用建议

- **先跑只读命令熟悉现状，不要一上来就跑真实提交**：`python main.py --status` 不开浏览器、只查数据库打印状态，是最安全的起步命令。
- **调试某个具体订单最安全的方式**：`python main.py --submit --orders <订单号>`，只处理指定的一个订单、点"取消"不真实提交，可以反复跑验证填表逻辑对不对，不会有副作用。
- **这个项目大量依赖 `print()` 输出做调试**，不是用什么高级日志框架——运行的时候把终端输出仔细看完，遇到问题往往终端已经把原因打出来了（比如"点击【XX】失败：重试 3 次后仍被遮挡"）。
- **Playwright 相关的报错是新手最容易卡住的地方**，常见的是 `TimeoutError`（等了很久还是没找到某个元素）——遇到这种报错，先怀疑是不是页面结构变了（网站改版）或者被弹窗挡住了，不要先怀疑代码逻辑本身写错了。
- **改动 `appeal_submit.py` 里跟页面选择器（`page.locator(...)` 里的字符串）相关的代码要格外小心**——这些字符串是从真实网页 HTML 里抠出来的，网站一改版就可能失效，改之前最好先在真实页面上用浏览器开发者工具核对一下元素还在不在。
- **`debug/` 和 `evidence/` 目录**（跑起来之后会自动生成）里存着大量运行过程中的截图，遇到"不知道当时页面长什么样"的问题，先去这两个目录翻一翻，比瞎猜有用得多。

## 9. 小术语表

| 术语 | 大白话解释 |
|---|---|
| Locator | Playwright 里"怎么找页面元素"的描述，不是元素本身，用的时候才会真的去页面上找 |
| Context / BrowserContext | 一个独立的浏览器会话，带自己的登录态/cookie |
| Modal / 模态框 | 弹出在页面上方、盖住其它内容的浮层（比如确认框、表单弹窗） |
| Selector | CSS 选择器字符串，用来告诉 Playwright"长得像这样的元素" |
| 拟人化操作 | 让程序的鼠标/键盘动作看起来更像真人（打字有间隔、鼠标轨迹不是直线），用来降低被网站风控识别成"机器人"的概率 |
| 熔断 | 某项操作连续失败达到一定次数后，主动停下来不再继续尝试，而不是无限重试 |
| 子进程 | 由当前程序启动的另一个独立运行的程序，Python 里用 `subprocess` 模块创建 |
| JSON Lines | 一种简单的文本通信格式：一行文本就是一个完整的 JSON 对象，靠换行分隔一条条消息 |
| 信号/槽（Signal/Slot） | PyQt5 里"某件事发生了"和"发生后要执行什么"之间的连接机制 |
| 主线程 / 后台线程 | 主线程负责界面显示和响应，耗时任务要挪到后台线程跑，不然界面会卡死 |
| dataclass | Python 标准库工具，自动帮你生成"接收几个字段"的类，少写样板代码 |
