## 一、这个项目是做什么的

拼多多（PDD）平台上，商家如果被买家投诉/给了负面评价，平台会给商家一个**有时间限制的"申诉"窗口**——商家可以说明情况，争取撤销处罚。人工处理这件事的完整流程是：

1. 去后台找出"现在还能申诉"的订单；
2. 打开这个订单，翻买家和客服的聊天记录，判断这次投诉到底是谁的责任、该用哪条理由申诉；
3. 写一段申诉说明文字；
4. 打开申诉表单，选好理由、填好文字说明、上传聊天记录截图当凭证；
5. 点提交。

如果同时管理几十上百个店铺，每天光是重复这一套流程就要花掉大量时间——**这个项目做的事，就是把上面这一整套流程自动化**，而且原生支持同时管理多个店铺。

**关键点：这不是调用拼多多官方提供的接口**（拼多多没有对外开放这类接口）。这个工具的做法是"像人一样操作浏览器"——真的打开一个 Chrome 浏览器窗口，代码控制它去点击、打字、翻页、截图，只是这些动作全部交给程序自动完成，不需要人一直盯着。

## 二、整体是怎么运作的

用一张大白话的流程图看懂这件事：

```
你（打开 GUI 窗口，或者敲一条命令）
   │
   ▼
调度器（决定"现在该轮到哪个店铺干活了"）
   │
   ├──▶ 店铺 A 的独立子进程 ──▶ Playwright 控制的浏览器 ──▶ 拼多多网站
   ├──▶ 店铺 B 的独立子进程 ──▶ Playwright 控制的浏览器 ──▶ 拼多多网站
   └──▶ 店铺 C 的独立子进程 ──▶ Playwright 控制的浏览器 ──▶ 拼多多网站
                                      │
                                      ▼
                          （处理过程中会去问 AI："这单该怎么申诉？"
                           "这个验证码上写的是什么字？"）
                                      │
                                      ▼
                          处理结果统一记进本地数据库（一个文件，不需要
                          另外装数据库软件），GUI/命令行随时能查进度
```

每一个订单，都会经过下面这三个阶段：

1. **采集**——打开"可申诉订单"列表，把订单号记下来。
2. **分析**——针对每个订单，去查它的聊天记录，交给 AI 判断"该用哪种理由申诉"、并让 AI 写好申诉文案。如果这单压根没有聊天记录，就用一段预设好的通用文案兜底，不用等 AI。
3. **提交**——打开这个订单的申诉表单，把 AI 给的理由和文案填进去，上传聊天记录截图，点击"提交"（也可以先只演练、点"取消"不真的提交，方便测试）。

**多店铺是怎么做到"看起来更像人"的**：程序不会把一个店铺的活干完再干下一个，而是像真人在多个账号间来回切换一样，各个店铺之间随机穿插着处理订单，还会在连续工作几个小时之后主动"休息"一段时间再继续——都是为了避免"一个不知疲倦的机器在不间断运行"这种规律本身被识别出来。

**申诉提交之后还没完**：拼多多审核一条申诉一般要 1-2 个工作日才出结果（通过还是驳回），上面三个阶段只负责"把申诉发出去"，不负责"回头看结果"。项目里另有一个独立的功能——**查询申诉结果**：按日期区间去申诉记录页把已经出结果的记录同步回来，跟"发申诉"这套流程完全分开、可以单独触发（GUI 里是"运行控制"页一个单独的按钮），不需要绑在一起用。

## 三、需要用到哪些技术

这是这份文档的重点部分。项目用到的技术大致分成这几类：

### 3.1 编程语言 & 环境管理

- **Python**——整个项目都是用 Python 写的。分成两个互相独立的运行环境：
  - **主项目**：Python 3.12，负责真正操作浏览器、调用 AI、读写数据库——最核心的部分。
  - **GUI（图形界面）子项目**：Python 3.11（因为界面用的库 PyQt5，稳定版本目前只支持到 3.11）。这部分只负责把数据"好看地"展示出来、接收你的点击操作，真要"打开浏览器做点什么"的时候，会另外启动一个主项目的 Python 进程去干，自己不碰浏览器。
- **uv**——新一代的 Python 包管理工具（类似速度快很多的 pip + 虚拟环境管理二合一），项目用它来安装依赖、把每个依赖包的精确版本锁定在 `uv.lock` 文件里，保证换一台电脑装出来的环境完全一致。

### 3.2 浏览器自动化

- **Playwright**（用的是它的"同步 API"）——核心引擎，真正负责"打开浏览器、点击按钮、输入文字、翻页、截图"这些动作。项目里所有跟拼多多网页打交道的代码，都是在这个库上面搭的。
- 光会"点点点"还不够，网站有自己的反自动化机制，所以项目专门写了一层伪装/拟人化手段：
  - 让浏览器"看起来"是一个真实用户在用真实电脑，而不是一段自动化脚本（伪装了几十项浏览器特征，比如显卡型号、屏幕参数这类信息）；
  - 模拟真人打字/移动鼠标的节奏——不是瞬间完成，而是有快有慢、偶尔停顿，鼠标轨迹也不是直线。

### 3.3 人工智能（AI）

项目用了**两个不同的 AI 服务**，分别负责两件不同的事：

| 用途 | 用的 AI 服务 | 具体做什么 |
|---|---|---|
| 判断申诉理由 + 生成申诉文案 | **DeepSeek** | 读聊天记录，判断这单该用哪条理由申诉，并且写一段几十字的申诉说明 |
| 识别验证码里的字符 | **火山方舟**（Volcano Ark，字节跳动旗下的 AI 服务） | 遇到"图片里有几个扭曲字母数字，输入正确内容"这种验证码时，识别出图上写的是什么 |

这两家服务底层都兼容同一套接口规范（OpenAI 定的接口格式），所以项目代码里只用了**一个** Python 库（`openai`）就能同时对接两家——不是说用了 OpenAI 自己的服务，只是"接口长得跟 OpenAI 一样"。

### 3.4 图像处理（另一种验证码，不用 AI）

拼多多还有一种"拖动圆环转到正确角度"的旋转验证码，这种**完全不用 AI**，纯靠数学计算解决：

- **Pillow**——图片处理库，负责把验证码截图解码成程序能处理的图片数据。
- **NumPy**——数值计算库，用来做图像匹配的运算（专业说法叫"归一化互相关"）。说白了就是让程序在电脑里"试"很多个旋转角度，找出哪个角度转出来的图案跟目标缺口最吻合，算出该转多少度、鼠标该拖动多远。

### 3.5 数据存储

- **SQLite**——一种不需要额外安装数据库服务器的数据库，本身就是一个本地文件（`state/pddchat.db`）。存了每个订单的处理状态、AI 分析出来的结果、每天每个店铺跑到哪一步了。选它的原因很实际：Python 自带支持，不用额外装任何东西，这个项目的数据量小到完全用不上更复杂的数据库。

### 3.6 图形界面（GUI）

给不写代码的运营人员用的桌面窗口程序（双击图标打开的那种软件窗口，不是网页），用到：

- **PyQt5**——做桌面窗口界面的库，四个功能页面（总览仪表盘、店铺管理、运行控制、报表/导出）都是用它搭的。
- **PyQtChart**——PyQt5 配套的图表插件，报表页面里那个柱状图用它画。
- **openpyxl**——用来生成 Excel 文件，报表页面"导出 Excel"这个按钮靠它实现（导出 CSV 用的是 Python 自带的功能，不需要额外的库）。

### 3.7 其它

- **python-dotenv**——从一个 `.env` 文件里读取密钥（就是上面提到的两个 AI 服务各自的 API Key），这样密钥不会被直接写死在代码里、也不会被提交进代码版本库。
- **ruff**——只在开发阶段用，检查代码风格、揪出常见的低级错误，不参与程序实际运行，运营人员完全不会接触到这个东西。

### 3.8 打包成安装包，给同事直接用

为了让同事不用自己装 Python、不用自己配置任何东西，项目会被整个打包成一个 Windows 安装程序（`.exe`，双击安装，装完就能直接用）：

- **Inno Setup**——制作 Windows 安装包的免费工具，负责把所有东西打包成一个安装文件。
- 打包出来的安装包里塞了不少东西，全都是为了让同事那台电脑"什么都不用另外装"：两份完整的、内嵌好的 Python 运行环境（对应上面说的 3.12 和 3.11 两个环境）、一份完整的 Chromium 浏览器（不用联网下载）、以及 Chromium 运行所需要的微软 Visual C++ 运行库安装包。

## 五、图形界面长什么样

打开 GUI 之后，左边是四个功能入口：

- **总览仪表盘**——纯展示，不用点任何东西，每 4 秒自动刷新。顶部 5 个大数字（店铺总数/今日已完成/待处理订单/今日已提交/今日失败），下面是每个店铺一张小卡片（登录状态、今天跑到哪一步、处理了多少单）。
- **店铺管理**——店铺列表，右键一个店铺可以：重新登录、停用/启用、重置今天的调度状态、给这个店铺单独设置"一次最多处理多少单"的上限、删除。
- **运行控制**——勾选这次要处理哪些店铺、设置同时最多开几个店铺的浏览器窗口、设置每天几点到几点允许自动运行、设置"连续跑几小时后休息一会儿"，点"启动"/"优雅停止"；另有一个独立的"查询申诉结果"按钮，跟提交流程无关，专门用来隔几天回头查一下审核结果出来没有。
- **报表/导出**——按店铺和时间范围筛选，看柱状图和详细表格，导出 Excel/CSV，点某一单还能看当时留存的截图凭证。

界面上每个按钮的详细用法，`使用文档.md` 里写得很细，这里不重复。

## 六、多店铺是怎么调度的（为什么好像有好几套"跑多店铺"的工具）

如果翻代码会发现有三个东西都跟"同时管理多个店铺"有关，容易让人疑惑，这里说清楚它们的关系：

- **`scheduler_core.py`**——真正的调度引擎，图形界面和命令行工具**共用同一份**。它的做法是：每个店铺开一个独立的子进程，各自控制一个浏览器；调度器按订单为单位（而不是按店铺为单位）在几个店铺之间随机切换，一单处理完就换下一个店铺，模拟真人来回切换账号的感觉；同时最多开几个店铺可以自己设置。
- **`run_shops_interleaved.py`**——命令行版本的外壳，本身没什么逻辑，就是把上面这个引擎包装成一条可以在命令行里敲的命令。图形界面的"运行控制"页面用的就是同一个引擎，只是外面套了个窗口界面而已。
- **`run_shops.py`**——一个更早期、更简单的版本，没有用上面那套共享引擎，自己单独实现了一遍"一个店铺处理完再处理下一个"（不是按订单交织，而是按店铺一个一个来，同一时间只开一个浏览器）。它还在，也能正常用，只是没有跟着升级到后来那套更灵活的引擎——可以理解成"老版本"和"新版本"的关系，不是两个功能不同的工具。

日常使用建议：图形界面（或者 `run_shops_interleaved.py`）就够用了，`run_shops.py` 了解一下"曾经有这么个更简单的版本"就好。
