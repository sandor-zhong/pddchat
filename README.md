# 拼多多商家申诉批量处理工具

## 提示词离线测试

项目根目录提供 `test_negative_prompt.py`（负向）、`test_reconsideration_prompt.py`（复议）、`test_aftersale_prompt.py`（售后）三个入口。例：`.\.venv\Scripts\python.exe test_negative_prompt.py --count 20`，将 `20` 改为 `50` 可测试50单。默认测试当前正式提示词，自动输出新旧话术对比 Excel、原始聊天及提示词快照；不打开浏览器、不提交申诉、不写业务数据库。

先用 `--list-only` 查看可用量。材料不足默认停止；加 `--allow-fewer` 按实际数量运行，或加 `--include-no-chat` 纳入正式兜底。自定义提示词、断点续跑和重新导出见[完整执行说明](docs/prompt_testing.md)。

## 环境准备

```bash
uv sync
```

首次运行前需在 `state/` 目录下有已登录的浏览器 Profile。

网页自动化的点击、移动、拖拽和滚轮统一使用 Windows 系统鼠标，用户能看到真实光标操作。Playwright 继续负责定位元素、读取页面和输入文字。运行时需要保持桌面解锁、浏览器可见，避免手动操作鼠标；多个任务的鼠标动作通过系统互斥锁串行执行。无法切换前台或目标被遮挡时会报错，不回退到浏览器虚拟鼠标。系统鼠标模式要求 `no_viewport=True`，不支持无头浏览器。

开发验证：运行 `python -m unittest tests.test_native_mouse`；在可交互 Windows 桌面设置 `PDD_NATIVE_MOUSE_SMOKE=1` 后运行同一命令，还会打开本地测试页验证真实点击、滑块拖拽、滚轮和新标签页。

运行控制页的“任务浏览器”可选择 Chrome / Chromium 或 Firefox。先停止任务及登录窗口后再切换；Chrome 保留原有目录，Firefox 登录状态保存在对应店铺目录的 `.firefox/` 中，首次切换需要重新登录。订单和申诉历史共用原数据库。

在“店铺管理”中选中或勾选一家店铺，点击“打开店铺”（也可右键选择“打开店铺（查看 / 调试）”），即可复用该店铺在当前浏览器中的登录状态，手动查看订单或其它后台页面。按 F12 / Ctrl+Shift+I 或右键“检查”可查看页面元素。窗口会一直保留到手动关闭；查看完后关闭浏览器或点击对话框中的“关闭浏览器”，登录状态会正常保存。该入口不自动执行采集、分析或申诉；打开期间占用现有运行锁，防止任务同时使用登录目录。

Firefox 使用 Playwright 配套版本，普通安装的 Firefox 不能直接用于此项目。开发环境执行 `uv run playwright install firefox`；Firefox 安装包内已带配套浏览器。Firefox 的表单输入使用浏览器原生填充并校验完整内容；Chrome 保留原来的剪贴板粘贴。

默认打包：运行 `./packaging/build_installer.ps1`，自动裁剪暂存运行时、更新源码并生成精简安装包，输出至项目根目录 `dist/pddchatSetup-0.1.0-lite.exe`。首次打包需先运行 `./packaging/build_runtime.ps1` 准备运行时；编译器未自动找到时用 `-CompilerPath` 指定 `ISCC.exe` 路径。`dist/` 已被 Git 忽略。

直接编译 `packaging/pddchat.iss` 也默认生成精简版到根目录 `dist/`。完整 Chromium 版需显式传入 `/DBundledBrowser`。Firefox 版：先运行 `packaging/build_runtime.ps1 -BrowserEngine firefox`、`packaging/stage_app.ps1`，随后给 Inno Setup 编译器传入 `/DFirefoxOnly`。

项目根目录 `.env` 需要分别配置业务分析和字符验证码使用的密钥：

```dotenv
DEEPSEEK_API_KEY=<DeepSeek 密钥>
QWEN_API_KEY=<qwen_client.py 所用的阿里千问密钥>
```

`ARK_API_KEY` 是旧火山方舟接口密钥，不能代替 `QWEN_API_KEY` 调用千问。

## 数据存储

订单状态、聊天记录、AI 分析结果统一记在 `state/pddchat.db`（SQLite，见 [db.py](db.py)）——**一个数据库文件覆盖所有店铺**，不再按店铺分文件、也不再有"文件存在与否"就是状态的隐式判断。截图类文件（`evidence/`、`debug/` 下的 PNG）仍然是文件，数据库里只存相对路径。

订单状态取值：`pending`（已采集未分析）/ `analyzed`（已分析未提交）/ `analysis_failed` / `simulated`（模拟提交，填表后点了取消）/ `submitted`（真实提交）/ `already_appealed` / `not_found` / `submit_failed`。

### 辅助查询功能

左侧“申诉数据报表”下方的“辅助查询功能”集中提供：

- 按提交日期查询各店铺负向申诉、复议、售后申诉的真实提交数量及合计；支持今天、昨天、任意历史单日或日期范围，没有提交的店铺也会列出。
- 按单个或全部店铺、申诉类型、起止日期查询通过率，日期按北京时间且包含结束当天。
- 显示每条范围内订单的当前审核结果、申诉记录标识、提交时间及来源、最后回查时间。
- 导出 Excel（查询说明、提交数量、通过率汇总、订单结果明细四张工作表），或导出逐订单 CSV。导出使用界面当前查询快照；修改条件后需重新查询。

提交数量、通过率及订单明细共用所选提交日期范围；查某一天时将起止日期设为同一天。查询直接匹配数据库已有订单/申诉记录的提交时间，历史订单也可查询，不依赖当天运行日志、采集时间或更新时间。只计真实提交、排除模拟提交，并优先使用程序提交时间，缺失时用平台申诉/复议时间补全；缺少可用提交时间的记录会提示数量且不计入区间。负向申诉沿用原报表的订单去重口径，复议和售后申诉按独立记录统计。

审核通过率＝计入通过数÷已出审核结果数；待审核、结果待确认及撤回不计入分母。售后“部分通过”默认计入通过数，可取消勾选只看完全通过。另列“通过占提交比例”，便于观察待审核较多时的实际提交产出。审核结果为已保存的最近一次回查状态；需要平台最新状态时，先在运行控制中回查结果。

## main.py — 全流程流水线

批量运行的店铺进程使用内存回收管理层：默认每 25 单，或店铺 Python 私有内存达到 768 MB、浏览器私有内存合计达到 1536 MB 后，在本单确认成功且仍有剩余订单时关闭旧工作进程及浏览器，使用同一登录目录启动新进程并恢复剩余队列。阈值不是强制内存上限；提交中、验证码等待、失败或结果待确认时不会仅因内存超限而重启。最后一单交给原流程正常收尾。

可通过进程环境变量 `PDDCHAT_RECYCLE_ORDERS`、`PDDCHAT_PYTHON_LIMIT_MB`、`PDDCHAT_BROWSER_LIMIT_MB` 调整。售后恢复会核对原页剩余记录，列表发生变化时停止并报告，不自动重扫或重新提交。手动单次 CLI 流程不经过此管理层。

每单内存与回收记录保存在 `state/logs/memory-<运行编号>-<PID>.jsonl`，包含进程 PID、父 PID、进程名、工作集、私有内存、线程和句柄数、系统剩余内存、源码指纹、运行编号及耗时。店铺标识使用摘要，订单结果只保留确认/未确认分类，不记录订单正文。界面及店铺管理层的独立后台线程每 30 秒采样；界面线程卡顿时仍可采样，但进程整体冻结或退出时无法保证采样。每个文件约 5 MB 滚动一次，保留一份旧文件；每五分钟清理超过 14 天或合计超过 100 MB 的旧内存日志（因此限制允许短暂超出）。界面进程不会被自动重启。

运行控制页的“导出内存诊断包”会导出上述结构化日志，排除原始 GUI 日志、数据库、登录资料、Cookie 和截图。异常时尽量在关闭程序前导出，并提供异常时间、任务类型、并发店铺数和包含 PID 的任务管理器截图。日志可以定位进程及订单边界的增长，不能直接证明某行代码泄漏；详细 Python 分配追踪暂未默认启用。复议和售后的回收事件另记入 `gui/state/logs/gui.log`，此文件不自动加入诊断包。

运行控制的“当前任务”表会显示每家店铺正在处理的订单和阶段。“查看”可前置该店铺当前的 Chrome 窗口；勾选“自动跟随表格中选中的店铺”后，仅在选中店铺开始处理订单时自动前置，默认关闭以免多店铺运行时抢焦点。“处理订单时自动置顶当前浏览器”默认开启，同一时刻只置顶当前正在处理的一家，本单结束、切换店铺或任务停止时自动取消。窗口定位沿店铺管理进程的子进程树查找，因此内存回收后启动的新浏览器仍能重新定位。Windows 可能按前台窗口策略拒绝自动前置，此时界面记录提示，任务本身不受影响。

三阶段：采集订单号 → 逐单（查聊天记录+AI分析 → 立刻填表提交）。不带阶段参数时默认走**逐单模式**——每个订单分析完立刻处理提交，再进入下一单；显式指定 `--collect`/`--analyze`/`--submit` 仍可分阶段批量执行（该阶段内部"全部订单跑完"再进入下一步），用于分步调试。

### 命令一览

| 命令 | 阶段 | 说明 |
|------|------|------|
| `python main.py` | 1+2+3 | 逐单模式：采集后逐单处理——分析完一单立刻填表提交（点取消，不真实提交） |
| `python main.py --confirm` | 1+2+3 | 逐单模式 + 真实提交申诉 |
| `python main.py --confirm --manual-captcha` | 1+2+3 | 逐单模式 + 真实提交 + 人工手动滑验证码 |
| `python main.py --reanalyze --confirm` | 1+2+3 | 逐单模式 + 真实提交，且强制重新分析已分析过的订单 |
| `python main.py --collect` | 1 | 仅采集可申诉订单号及问题类型（批量） |
| `python main.py --analyze` | 2 | 仅查聊天记录 + AI 分析（批量，全部订单跑完；自动从数据库读取待分析订单） |
| `python main.py --submit` | 3 | 仅填表（批量，点取消，不提交） |
| `python main.py --submit --confirm` | 3 | 仅填表 + 真实提交（批量） |
| `python main.py --collect --analyze` | 1+2 | 采集 + 分析（批量） |
| `python main.py --analyze --submit` | 2+3 | 分析 + 填表（批量，非逐单交织） |
| `python main.py --shop <店铺> --aftersale-appeal --max-orders 10 --confirm` | 售后申诉真实提交 | 完成取证和表单校验后点击“提交申诉”；GUI 中会先显示不可撤回警告 |

不带 `--collect`/`--analyze`/`--submit` 中任何一个时（哪怕只加了 `--confirm`）才会走逐单模式；一旦显式指定了其中任意一个，就会退回原来的分阶段批量流程。

### 辅助参数

| 参数 | 说明 |
|------|------|
| `--order-file <文件名>` | 指定 output/ 下的 JSON 文件作为订单来源（跳 Phase 1 时用） |
| `--orders <订单号...>` | 直接指定订单号，空格分隔 |
| `--manual-captcha` | 关闭自动破解验证码，改由人工手动滑动 |
| `--reanalyze` | 逐单模式下强制重新分析数据库里已有结果的订单（默认跳过已分析订单，直接进入提交） |
| `--status` | 不开浏览器，直接查数据库打印订单状态汇总（不加 `--shop` 时跨店铺汇总），详见"数据存储"一节 |
| `--check-appeal-results` | 回查负向申诉结果；必须搭配 `--shop`。启用提交时间范围时优先按 ticketSn 查询详情，否则扫描页面默认日期范围并补查漏查订单；`--since-days` 仅为旧参数兼容保留 |
| `--aftersale-appeal` | 运行独立的售后申诉真实提交流程，必须搭配 `--confirm`。GUI「运行控制 → 售后申诉」支持设置同时运行店铺数；多个浏览器保持打开，但订单严格逐单轮转，并提供安全停止按钮 |

售后申诉使用独立的 `aftersale_appeal_records` 数据表，不会覆盖现有首次申诉或复议状态。列表会保存订单编号、订单信息、发货状态、实收金额、退款金额、退款时间、申诉项和倒计时。货款申诉优先选择“消费者反馈商品存在质量问题，但凭证不足”，没有该选项时选择“非以上申诉原因”；运费申诉固定选择“退货运费 / 消费者无理由退货，退货运费不应商家承担”。退款申请单截图保存到 `evidence/<店铺>/<订单>/aftersale_<售后编号>/`，填表现场保存到 `debug/<店铺>/`。

售后申诉列表初次进入、翻页及恢复任务时，都等待有效订单或稳定空状态。短暂出现“暂无相关订单”不会立即结束：必须无加载遮罩、空提示连续稳定至少 3 秒才确认无订单；加载重新出现、空提示消失或表格替换都会重新计时。有订单则继续处理，无需等满 3 秒；每轮最长等待 20 秒，共尝试 2 轮，仍无法确认时保存现场并报错，避免按空列表跳过。

售后详情页同时出现“维权申诉”和“极速退款申诉”时，只点击“维权申诉”；只有“极速退款申诉”入口时才使用该入口。

同时勾选“货款申诉”和“纠纷退款率申诉”时，申诉原因固定使用“非以上申诉原因”；如果表单已选中该原因则直接保留，否则切换后读回校验。

「批量查询售后结果」（`--shop <店铺名> --check-aftersale-results`）会将“部分通过”原样保存为审核状态，并打开该申诉的详情新标签页，以“返还金额”更新数据库金额、审核历史和报表，读取后关闭详情页。其他状态继续使用列表金额。已保存的“部分通过”记录也会重新核对，修正旧版保存的申请金额；详情读取失败时保留“部分通过”状态、金额留空并记录原因，下次查询再次补全。

查询直接进入平台售后申诉结果列表，不经过聊天页，只匹配并回写本地数据库中已有且确实提交过的售后申诉记录。平台有而本地没有的申诉会被忽略，不会自动补录；已出结果的本地记录也会重新核对。程序逐页查询（默认最多 100 页，达到上限会提示），日志分别显示平台检查数、忽略的非本地申诉数和本地未匹配数。本地没有待回查记录时直接结束，不打开平台页面。

“运行控制 → 结果回查”支持勾选“按提交时间查询（三类结果共用）”，设置北京时间起点（含该时间），设置自动保存，手动与定时查询都会使用。本批次启动后固定使用当时的设置，运行中调整只影响后续批次。已知提交时间早于起点的本地记录会跳过；缺少有效提交时间的历史记录保留回查，以免漏查。

启用时间范围后，负向申诉对有 ticketSn 的目标订单直接回查所有相关详情，避免受列表默认日期限制；没有 ticketSn 的目标仍走列表，无法定位时保留“结果待确认”。复议和售后按完整申诉记录匹配，目标全部查齐就停止翻页；未查齐时继续到平台末页，不再因原来的 50/100 页上限截断。不会仅因看到一条较早记录就停止，避免平台排序变化时漏查。翻页重复或无法更新会报错；到末页仍未匹配的目标在界面标记为“未查齐”。未启用时间范围时保留原页数上限。

命令行三类回查均支持 `--result-submitted-since "2026-10-01 00:00:00"`，省略时使用已保存设置，显式传 `--result-submitted-since all` 表示不限制提交时间。

“立即查询申诉结果”只回查本地已提交且待出结果的负向申诉，不会自动导入平台历史订单。启动前先检查本地状态和提交时间：没有符合条件的订单时不打开浏览器，并说明是没有待查记录还是时间范围排除了记录；有目标时直接进入申诉列表或详情，不再打开聊天记录页验证登录。查询失败时弹窗显示具体原因，不会仅显示“更新 0 条”。

批量查询复议结果、批量查询售后结果也先检查本地记录和提交时间，无目标时不启动浏览器；有目标时直接打开对应结果页面并检测登录状态。汇总区分“无需查询”“未查齐”和“查询失败”，显示各店铺原因并保留成功更新的数量。未启用时间限制时，目标未匹配或达到售后翻页上限也会提示未查齐。售后沿用原规则，已出结果的本地申诉仍可回查。

结果查询优先根据实际目标页面是否重定向到 `mms.pinduoduo.com/login`（兼容末尾斜杠和查询参数）判断登录失效，同时检测原网址内显示的扫码/账号登录面板。等待结果内容时也持续检查跳转；网络超时或空列表不会直接认定为未登录。

若页面显示登录区域及可见的“扫码登录 / 账号登录”入口，查询会明确提示登录失效，并引导到「店铺管理 → 右键店铺 → 重新登录」。详情页跳回登录页也会中止当前店铺查询，不会把登录失效当作没有订单或返还金额缺失。

「运行控制 → 结果回查」可设置“售后结果查询间隔”（1～60 秒，默认 3 秒，自动保存）。每次翻页、打开部分通过详情，以及 GUI 切换下一家店铺前都会等待该间隔；读取当前列表中的普通行不额外等待。命令行可用 `--aftersale-query-interval 5` 指定 5 秒，省略时使用已保存设置。

售后结果表格出现后，会等待加载提示消失以及完整表头、订单数据或明确空状态，最长 45 秒。翻页后也会等待新页数据就绪，避免把加载占位表误报为缺少“审核状态”或零条记录。持续加载、真实缺列和翻页未更新会分别给出对应错误并保存现场截图。

## run_shops.py — 多店铺串行随机调度器

自动管理多个已登录店铺：一次只操作一家店，做完后随机跳到下一家，所有店铺跑完一轮后重新随机洗牌继续，直到手动停止。

### 前置条件

每个店铺需在 `state/profiles/` 下有自己的目录（首次用 `python main.py --shop <店铺>` 跑一次即自动创建），调度器会自动扫描这些目录作为调度列表，无需手动维护。

### 命令一览

| 命令 | 说明 |
|------|------|
| `python run_shops.py` | 无限循环串行调度：每轮随机洗牌，逐店跑完 main.py 默认流程（逐单处理），Ctrl+C 停止 |
| `python run_shops.py --once` | 只跑一轮就退出（先验证调度链路再挂长跑） |
| `python run_shops.py --confirm` | 透传给每家店：填完表单真实提交申诉（⚠ 会真实提交） |
| `python run_shops.py --confirm --manual-captcha` | 真提交 + 每家店人工手动滑验证码 |

### 调度行为

- 同一时刻只操作一家店铺：调度器以子进程方式运行 `python main.py --shop <店名>` 并阻塞等待其完成
- 每轮执行前对店铺列表 `random.shuffle` 洗牌，实现"一家做完随机跳下一家"
- 一轮跑完自动重新洗牌开始下一轮，无限循环
- 某店铺子进程异常退出（非零退出码）时记录并继续下一家，不中断整轮
- `Ctrl+C` 停止调度；运行中的店铺子进程随 Ctrl+C 一起终止

### 调度粒度

换店铺的粒度是**一整家店的一整轮**：调度器调用 `main.py --shop <shop>` 时不带任何阶段参数，因此每家店内部走的是 main.py 默认的**逐单模式**（分析完一单立刻提交，再处理下一单），但要等这家店的订单**全部**处理完才会轮到下一家店——不是"提交完一单就跨店铺切换"。真正"提交完一单随机换店铺"见下面的 `run_shops_interleaved.py` 一节。

### 与手动多店并跑的区别

| | 手动多店并跑 | 串行调度器 |
|------|------|------|
| 同时操作店铺数 | 多个（易触发风控） | 同一时刻仅 1 个 |
| 店铺顺序 | 手动分配 | 每轮随机 |
| 运行方式 | 多个终端各自盯 | 一个终端挂机即可 |

## run_shops_interleaved.py — 逐单跨店随机调度器（固定并发上限）

跟 `run_shops.py` 效果不同：这个脚本才是真正"提交完一单就随机换另一家店"，调度粒度精确到**单个订单**，而不是"整店一整轮"。而且**同时最多只开 N 家店铺的浏览器**（默认 4，`--max-concurrent` 可调）——不管这次发现了多少家店铺，并发数量都不会超过这个上限；哪家店铺订单处理完，就关掉它的浏览器，从还没处理过的店铺里挑一个顶上来补位。

### 前置条件

同 `run_shops.py`：店铺需要在 `state/profiles/` 下有自己的登录态目录。

### 命令一览

| 命令 | 说明 |
|------|------|
| `python run_shops_interleaved.py` | 无限循环：同时最多开 4 家店铺，一轮所有店铺都处理完一遍就重新开始下一轮 |
| `python run_shops_interleaved.py --max-concurrent 6` | 同时最多开 6 家店铺（默认 4） |
| `python run_shops_interleaved.py --once` | 只跑一轮（所有店铺都处理完一遍）就退出（先验证调度链路再挂长跑） |
| `python run_shops_interleaved.py --confirm` | 透传给每家店：真实提交申诉（⚠ 会真实提交） |
| `python run_shops_interleaved.py --confirm --manual-captcha` | 真提交 + 每家店人工手动滑验证码（会自动放宽调度器的响应超时到 30 分钟，给人留出反应时间） |
| `python run_shops_interleaved.py --reanalyze` | 透传给每家店：强制重新分析数据库里已有结果的订单 |

### 实现机制

- 每个"在池子里"的店铺各自一个**常驻**子进程（`python main.py --shop <shop> --serve`），浏览器全程开着，不是每单都重启；但**池子大小有上限**（`--max-concurrent`，默认 4）——店铺数量再多，同时打开的浏览器也不会超过这个数；
- 某家店铺这一轮的订单处理完（收到 `queue_empty`）：立刻关掉它的浏览器子进程、让出名额；如果还有没处理过的店铺在排队，马上开一个新的顶上来（同样要先 `init` 采集才能加入轮转）；
- 子进程处理完一单不退出，挂起等调度器下一条指令——调度器和子进程之间通过 stdin/stdout 上的一个极简 JSON Lines 协议通信（`init` 采集订单号 / `next` 处理下一单 / `stop` 关浏览器退出）；
- 调度器在"池子里当前打开的几家"之间随机点名"该你了"，且**不会连续两次点同一家**（只剩一家在池子里时除外）；无论是一开始填满池子，还是店铺做完之后补位新开浏览器，都是严格一家一家串行处理，不会两家同时 `init`；
- 因为浏览器操作完全在各自子进程里单线程执行，"同一时刻只有一家店在操作"是协议本身保证的，不依赖任何锁；
- 某店铺子进程超时无响应或异常退出时，记录后关闭它并让位给排队里的下一家，不影响其余店铺；`Ctrl+C` 或 `--once` 收尾时会给所有仍存活的子进程发 `stop` 优雅关闭浏览器，超时未退出的兜底 `terminate()`。

## 调试建议

```bash
# 逐单模式的安全流程：先不加 --confirm 跑一遍看结果
python main.py                                     # 逐单：采集 + 逐单分析 + 模拟提交（点取消）

# 用 --status 人工抽查数据库里的分析结果/提交状态，确认无误后加 --confirm 重跑
python main.py --status --shop <店铺>
python main.py --confirm                           # 已分析过的订单自动跳过重新分析，直接真实提交
```

`--confirm` 单独重跑时，数据库里已经有分析结果的订单不会重新调用 AI——所以"先跑一遍看结果、再加 --confirm 重跑"不会浪费一次额外的模型调用。

分阶段批量调试（原有流程，仍然有效）：

```bash
# 最安全的调试流程：逐步执行
python main.py --collect                          # Step 1: 只采集订单号
python main.py --analyze                          # Step 2: 查聊天 + AI 分析
python main.py --submit                           # Step 3: 填表但点取消，检查结果

# 确认无误后，指定单个订单号调试验证
python main.py --submit --orders 260805-552620593590168
```

`--submit` + `--orders` 是最安全的调试方式——可反复在同一订单上验证填表逻辑而不产生副作用。

## 阶段说明

```
采集阶段 (run_appeal_batch.py / main.py --collect)
  ├── 默认只读"可申诉"标签页第一页（collect_all_appealable_order_numbers
  │   的 max_pages 默认值是 1）——每天新出现在第一页的订单处理完就够，
  │   不用每次都翻遍所有历史积压页；要恢复翻页可以显式传更大的 max_pages
  ├── 提取订单号 + 问题类型（商品问题/服务问题）
  └── 记录到数据库（db.record_collected，状态 pending）

逐单循环（默认模式；显式加 --analyze / --submit 时改为分两轮批量执行，
          即"分析阶段"全部订单跑完，再进入"提交阶段"全部订单跑完）
  对每个订单依次：
  ├── 分析：打开聊天页面抓取聊天记录 → 无记录的截图存证，有记录的调用
  │        大模型分拣申诉凭证类型并生成申诉文案 → 写入数据库
  │        （db.record_analyzed，状态 analyzed；已有分析结果的订单默认
  │        跳过，除非加 --reanalyze）
  └── 提交：搜索订单号 → 一个订单号可能对应多条独立的申诉记录（商品问题
           一条、服务问题一条，甚至同类型不止一条），逐条处理 → 每条记录
           自动判定 A/B/C 及 TERMINAL_STATUS_MARKERS 登记的终态（目前有
           ALREADY_APPEALED/EXPIRED/REJECTED）→
           按问题类型填写对应表单
             ├── 商品问题：选申诉原因 → 填说明 → 上传凭证
             └── 服务问题：选"其他" → 填说明 → 上传凭证（渐进渲染）
           → 默认点"取消"（状态 simulated），加 --confirm 则真实提交
           （状态 submitted）→ 落库到 appeal_records（记录级别）→
           下一条记录 → 这个订单号处理完 → 处理下一单
```

## 申诉详情页状态对照

| 状态 | 识别条件 | 表单类型 |
|------|----------|----------|
| A | "当前平台未采取实际处理措施" | 模态框：radio + textarea + 图片 |
| B | `detail_confront_new_status` + `<a>` 链接 | 模态框：二次确认 + radio(渐进) + 图片 |
| C | `detail_confront_new_status` + `<button>` | 新页面：select 下拉 + textarea + 图片 |
| ALREADY_APPEALED | 状态文本含"已申诉" | 跳过 |
| EXPIRED | 状态文本含"超时未申诉"（申诉窗口已过期、已被处罚） | 跳过 |
| REJECTED | 状态文本含"申诉未通过"（申诉过但没通过、已被处罚） | 跳过 |

以上"跳过"类状态的识别标记集中在 `appeal_submit.py` 的 `TERMINAL_STATUS_MARKERS` 字典里，新增一种只需要在那加一行（`main.py` 对应的 `_TERMINAL_STATUSES` 字典也加一行），不用改判断逻辑本身。
